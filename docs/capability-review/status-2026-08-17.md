*A dated snapshot of one work period, not a register.*

status and for the shared suite's counts; this file records what moved,

## Headline

G1 phase 3 is **merged**. Phases 4 and 5 are **written and in parity but
unfinished** — they have no spec rows, and that gap is the whole of the
remaining coverage debt in both ports.

The period's surprise was not the constraint algebra. Allowing

defects in the function-call comma group**, three of them silent wrong
answers or crashes, in code that had been shipped for weeks.

- **`len` → `length`**: a plain rename, no alias — the atom was one

  strict; data is parsed with the full grammar), and five probed
  constraints on what a shared spec row can pin.

One rule came out of implementing phase 3 that the design did not have:
**sizing atoms fold last**. An order atom may decide the moment it meets
a scalar, because meeting further scalars can only narrow; a sizing atom
cannot, because meeting further containers *grows* the member set. So
`a: length(2)` / `a: {x:1}` / `a: {y:2}` counted `{x:1}` alone and
refused the fragment layering the language exists for. Recorded in
`docs/reference-language.md` and as a departure in the register.

**Phase 4 — cross-field arguments, residuation.** An atom whose
arguments have not settled becomes `pending` and resolves in `unify`,
mirroring the discipline `FuncBaseVal` already follows. `min($.lo)`,
`min(1+1)`, `length($.n)`, `re($.p)`, chained and forward references all
settle and then normalise; an unresolvable reference reports `no_path`.

deduplicated or reordered, checked against a *clone* of the finished

since "needs the whole value" is what `length`, `unique` and `must`
share.

## The parser defects

Three, all in the function-call comma group, all pre-existing, all
latent on `main` because a reference argument used to be refused before
it could reach the algebra. Phase 4 is what made them reachable.

| defect | port | severity | resolution |
|---|---|---|---|
| Operator expressions in a comma group handed over unreduced | TS | wrong value | fixed upstream, `@tabnas/expr` 0.5.4 |
| `addition-infix` read the rule's open token unguarded | Go | **panic** | fixed here, `0feb17c` |
| Arguments after a single-segment `$.x` dropped | TS | **silent wrong answer** | fixed upstream, 0.5.4 |

The third is the one that mattered: `a:neq($.z,3) a:3` **admitted 3**.
`neq` takes one-or-more arguments, so the arity check could not notice a
dropped exclusion, and the result was well-formed and wrong. It is
reachable on `main` today through `neq` alone.

Two were reported upstream as [tabnas/expr#42](https://github.com/tabnas/expr/pull/42)
and [#43](https://github.com/tabnas/expr/pull/43), fixed there, and
released as 0.5.4. Adopting it needed one more repair on our side: the
"stop skipping implicit-list members" half had landed in the TypeScript
runtime but not the Go one, so `k2.b K:1` unified to `[[nil,"k2","b"]]`
as a *value* in Go while TypeScript raised `no_path`. `asValDepth` now
reduces an op-headed slice through the parser's own `evaluate`.

Three workarounds became dead code and were removed, each found by the
coverage gate rather than by memory: `reduceOps`, the `OP_MARK` guard in
`rawToVal`, and the `ConjunctVal` arm of `countArgState`.

### In this repository — TS/Go divergences

1. **Go takes an unrecoverable fatal stack overflow** on a `**` prefix
   chain followed by `.` and a non-identifier operand — `**.true`,
   `**.null`, `**.[1]`, `**.{a:1}`. Infinite self-recursion in
   `PrefVal.Canon` (`go/pref.go:57`), a `PrefVal` whose `peg` is itself.
   Not recoverable, so no error surfaces: the process dies. TypeScript
   handles all of them. **This is the one to fix first.**
2. `a:f(1)(2)` generates `{"a":2}` in Go and throws `unknown_function`
   in TypeScript — a juxtaposed call paren silently replaces the value.
3. `path([1,2])` is refused with `invalid-arg` in TypeScript and passed
   through in Go, which then generates the argument as the result.
4. A built-in wrapping an unresolvable reference, as the whole document,
   generates `null` in Go and is refused with `no_gen` in TypeScript —
   though both produce the identical unify canon first.
5. A dot chain of **three or more** segments in an implicit top-level
   list resolves to *different references* in the two ports: `a.b.c d:1`
   is `[.b.c]` in TypeScript and `[.a]` in Go. The two-segment case
   agrees, which is why earlier probing missed it.

### Upstream — `@tabnas/expr` 0.5.4

Both verified by running the code, neither reported yet.

1. **Go calls `evaluate` twice** for every implicit-list member except
   the last, when the list is inside a paren. TypeScript added an
   `EVALUATED` memo and a regression test; the Go port received the same
   in-place reduce with neither. aontu *appears* insulated — our
   evaluators return `Val`s, which are neither slices nor op-arrays, so
   the second pass is a no-op — but that is reasoning, not evidence, and
   has not been verified end to end.
2. **TypeScript's AC hook writes `r.parent.node` with no `NoRule`
   guard** — the same class of defect #43 fixed in Go, left live in the
   other runtime.

#### Resolved upstream (2026-08-17, later)

Both are **fixed** in `tabnas/expr` ([#44](https://github.com/tabnas/expr/pull/44)),
along with a third defect the work to fix them uncovered, **released as
0.5.5** and **adopted here in both ports**.

**1 is fixed, and the diagnosis above was half right.** The memo was
missing, but it was not the cause. TypeScript's AC hook reduces a member
in place *into the list*, because the rule collecting the list is the
expression's own parent there; the Go grammar interposes a `val` rule
between a paren argument and the paren collecting it, so the hook only
ever saw the member's own op-array, wrote the result where the list does
not read it, and left the raw op-array to be reduced again when the
enclosing expression closed. The fix reaches one level further up, and
only when that list still ends with the exact node about to be reduced —
identity by shared `*Op`, not shape. Go also gained the `EVALUATED` memo,
scoped to one parse via `ctx.U` since Go has no weak map.

**aontu's insulation is now evidence rather than reasoning.** Reducing 36
sources through both runtimes with a rewriting evaluator that records
every call: against the previous Go, **zero output differences and 16
fewer calls**, every removed call a duplicate. The wrong-value risk was
nil, as we reasoned — but the callback ran twice, so any evaluator with
an effect (an allocation counted, a diagnostic recorded) ran it twice
too, which our reasoning did not cover.

**2 is fixed as a latent hazard, not a live defect.** No shape was found
that reaches that write with `NORULE` as the parent; the guard matches
Go's and the 36-source differential is byte-identical before and after.

**3 — new, and worse than either.** With Go corrected the two runtimes
agreed on every probe source but one, and there it was **TypeScript**
that was wrong: `1+2*3,4` parsed as `[["*",2,3],4]`. The `1+` was gone
from the tree — not mis-associated, not unreduced: absent, with nothing
to signal it. `topList` seeds a top-level implicit list from the rule
that meets the separator, which is the last node prattify built; for a
flat first member that node *is* the whole expression, but for a
right-leaning one it is a sub-expression. Only a bare top-level list
reaches it — `[1+2*3,4]`, `f(1+2*3,4)` and `{a:1+2*3,b:4}` were all
correct. Thirteen rows added to the shared fixture, ten of which fail on
0.5.4; the three that pass are exactly the shapes the defect cannot
reach, which is also why the existing 24 rows missed it — every one of
their first members is a same-precedence `+` chain.

Verified twice against this repository — first with `@tabnas/expr`
pointed at the fixed checkout, then again on the **released 0.5.5** once
it was adopted: **Go all packages green, TypeScript 2,513 green**, `go
vet` clean, and the Go module still building under
`GOTOOLCHAIN=go1.24.7`. Confirmed through our own installed dependency
that the fixed behaviour is what we now get: `1+2*3,4` parses as
`[["+",1,["*",2,3]],4]`, and no operator reaches an evaluate callback
twice.

One thing the first run turned up, now closed: `ts/node_modules/@tabnas/expr`
had been sitting at **0.5.1** while `ts/package.json` pinned 0.5.4, so a
local `npm test` was not exercising the version this repository claimed
to have adopted. Local staleness rather than a repository defect, and a
clean install fixed it — but worth remembering that a stale install
looks exactly like a passing suite. Two dependency-version traps in one
day, the other being a stale `ts/dist` upstream; neither is visible from
a green run.
